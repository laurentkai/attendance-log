# Automatic deployment to the Lightsail VPS

This guide documents the production deployment implemented by
`.github/workflows/deploy.yml`.

## Architecture

- GitHub Actions starts a deployment on every push to `main`, or on a manual
  `workflow_dispatch` run.
- A self-hosted GitHub Actions runner runs directly on the AWS Lightsail VPS.
- The runner deploys the Attendance Log repository from its existing production
  checkout on the VPS. It does not create a second checkout.
- Docker Compose builds and runs the Node.js application and PostgreSQL.
- nginx is the public HTTPS entry point and proxies to the application on the
  VPS loopback interface.
- Production configuration and secrets remain in an untracked `.env` file in
  the VPS checkout.

## Install and register the self-hosted runner

1. In the Attendance Log GitHub repository, open **Settings > Actions >
   Runners**, select **New self-hosted runner**, and choose the VPS operating
   system and architecture.
2. On the VPS, create a permanent runner directory and run the download and
   registration commands generated by GitHub.
3. During registration, add the custom label
   `attendance-log-production`. The resulting runner must have these labels:

   - `self-hosted`
   - `linux`
   - `attendance-log-production`

   GitHub adds the standard `self-hosted` and `linux` labels automatically for
   a Linux runner. The production label is project-specific.
4. From the runner installation directory, install and start the supplied
   systemd service:

   ```bash
   sudo ./svc.sh install
   sudo ./svc.sh start
   sudo ./svc.sh status
   ```

When the runner log contains `Listening for Jobs`, it is connected to GitHub
and ready to accept a deployment.

The systemd unit name is generated from the GitHub organization, repository,
and runner name. Use the service name shown by `sudo ./svc.sh status` when
following its logs:

```bash
sudo journalctl -u <runner-service-name> -f
```

## Configure the repository variable

Create the required GitHub Repository Variable here:

**Repository > Settings > Secrets and variables > Actions > Variables > New
repository variable**

- Name: `PRODUCTION_DEPLOY_PATH`
- Value: the absolute path to the existing Attendance Log production checkout,
  for example:

  ```text
  /home/ubuntu/apps/attendance-log
  ```

Do not use `~/...`. From the production checkout on the VPS, run `pwd` and use
its exact absolute output as the value.

## Prepare the production checkout

Before enabling automatic deployment, the path configured above must:

- already exist and be the Attendance Log Git repository;
- use `origin` for the repository fetched by the workflow;
- have no local modifications to tracked files;
- contain the production `.env` as an untracked file;
- be readable and writable by the runner service user;
- allow that user to run Docker and `docker compose`;
- allow `git fetch origin` non-interactively.

The workflow deliberately runs `git reset --hard origin/main`. Any tracked
changes made directly in the production checkout will be discarded. It does
not remove the untracked `.env` file.

## Production `.env`

The production checkout uses `.env` for environment-specific configuration.
At minimum, its network/runtime values should include:

```dotenv
NODE_ENV=production
BIND_ADDRESS=127.0.0.1
PORT=3000
```

The application is bound to localhost because nginx is the public HTTPS entry
point. Database credentials, `SESSION_SECRET`, `APP_BASE_URL`, and any other
deployment secrets also remain in `.env` according to `.env.example`.

Never commit `.env` or copy its secret values into the workflow. The workflow
checks that `.env` exists and is not tracked by Git.

## Deployment triggers and concurrency

- A push to `main` triggers deployment automatically.
- To deploy manually, open **Actions > Deploy production**, choose **Run
  workflow**, select `main`, and start the run.
- The `attendance-log-production` concurrency group permits only one production
  deployment at a time.
- `cancel-in-progress: false` means a new push waits; it does not cancel a
  production deployment already running.

Deployment history, step output, duration, and failures are available under
**Actions > Deploy production** in GitHub.

## Deployment sequence

The runner changes into `PRODUCTION_DEPLOY_PATH` and executes:

```bash
git fetch origin
git checkout main
git reset --hard origin/main

docker compose build
docker compose run --rm app npm run migrate
docker compose up -d
```

Migrations run after the image is built so the one-shot container contains the
migration files from the new release. They run before `docker compose up -d` so
the database schema is ready before the updated long-running application is
started or recreated.

The workflow then runs `docker compose ps` and polls `/health` from inside the
application container. Build, migration, startup, or health-check failure makes
the workflow fail. On a health-check failure, it prints the last 100 application
log lines.

## Persistent-data safety

Normal automatic deployment preserves:

- `postgres_data`, containing PostgreSQL data;
- `app_secrets`, containing the file-backed application encryption key and
  installation instance identity;
- the untracked production `.env` file.

The workflow does not remove Docker volumes and never runs `docker compose
down -v`.

> Do not run `docker compose down -v` as routine maintenance. The `-v` option
> removes persistent Compose volumes and can destroy the database and generated
> application encryption key.

## Troubleshooting

### Job stays waiting for a runner

Check that:

- the runner is online and idle under **Settings > Actions > Runners**;
- it has the `attendance-log-production` label;
- `sudo ./svc.sh status` reports a running service;
- its status or journal contains `Listening for Jobs`.

### `PRODUCTION_DEPLOY_PATH must be configured as an absolute repository variable`

From the Attendance Log production checkout on the VPS, run:

```bash
pwd
```

Store the exact output as the `PRODUCTION_DEPLOY_PATH` Repository Variable. Do
not use `~`, a relative path, or the runner installation directory unless it is
also the actual production checkout.

### Runner service commands

Run these commands from the runner installation directory:

```bash
sudo ./svc.sh status
sudo ./svc.sh stop
sudo ./svc.sh start
```

To restart the service, stop it and start it again. Follow its systemd log with:

```bash
sudo journalctl -u <runner-service-name> -f
```

### Docker permission errors

The runner service user must be able to run `docker` and `docker compose`
without an interactive privilege prompt. Correct that user's Docker access,
restart the runner service if its group membership changed, and verify access
from the same user account used by the service.

### Git permission or authentication errors

The production checkout must be able to run this command non-interactively as
the runner service user:

```bash
git fetch origin
```

Verify the `origin` URL and the VPS user's repository authentication. Do not
place repository credentials in the workflow file.

### Health check failure

From the production checkout, inspect service state and logs:

```bash
docker compose ps
docker compose logs --tail=100 app
docker compose logs --tail=100 postgres
curl http://127.0.0.1:3000/health
```

The expected health response reports `status` as `ok` and `database` as
`connected`. Also inspect the failed workflow step, because migration or startup
errors may occur before the health check.

## Manual deployment fallback

If GitHub Actions is temporarily unavailable, run the equivalent deployment
from the existing production checkout:

```bash
git fetch origin
git reset --hard origin/main
docker compose build
docker compose run --rm app npm run migrate
docker compose up -d
```

Then verify it with `docker compose ps` and the `/health` command shown above.
This fallback preserves `.env` and the named volumes in the same way as the
workflow.

## Disable or remove the runner

To temporarily stop the runner, use the supplied service script from its
installation directory:

```bash
sudo ./svc.sh stop
```

To remove its systemd service:

```bash
sudo ./svc.sh stop
sudo ./svc.sh uninstall
```

If the runner is still registered, remove it from **Repository > Settings >
Actions > Runners** and follow the removal instructions GitHub provides for that
runner. Removing the runner does not require deleting the Attendance Log
checkout, `.env`, or either persistent volume.

## Security notes

- A self-hosted runner executes repository workflow code directly on the VPS;
  use it only for a trusted Attendance Log repository and trusted workflows.
- Keep the repository private or otherwise strictly control who can modify
  workflow code.
- Keep `.env` and all deployment credentials outside Git.
- Do not expose the Docker socket or this runner to untrusted repositories or
  workflows.
